# Target architecture

The reimplementation is built up layer by layer. The simulation core knows neither DirectX nor Windows UI. This allows it to be tested deterministically, quickly and without graphics.

1. `CnCNew.Archives` serves only as a local import tool for the existing game data.
2. An import VFS merges loose files and BIG archives once in original priority and materialises normal files. The runtime knows no BIG containers.
3. `CnCNew.Content` opens exclusively normal files at run time on the basis of `content-manifest.json`. The project references neither the import VFS nor `CnCNew.Archives`.

`CnCNew.Formats` adds the engine-independent readers for STR, MAP/SCB/WAK, WND, DDS, ANI,
WAV, MP3 and BIK. `CnCNew.Import` is the only connecting layer between these readers,
import VFS and archives: it builds the dependency graph and publishes schema 2 atomically.
`CnCNew.Content` validates canonical `asset://` IDs, case collisions, hashes, overlay origin,
importer options, artefacts, dependencies and typed fallbacks. Schema 1 is exclusively
a visible migration read path. Logical paths and Windows-safe physical names stay
separate. The complete contract is in `docs/CONTENT-PIPELINE.md`.

4. `CnCNew.Data` translates INI syntax through a runtime-path-based `IDefinitionSource` into the
   immutable `CompiledDefinitionGraph`. Includes, conditions, overlay inheritance and
   Add/Remove/ReplaceModule are evaluated before the contract boundary. Definitions have
   stable typed IDs, unit values, module configurations, source positions and validated
   reference edges; `IniNode` does not leave the compiler. `ModuleRegistry` keeps the catalogue of all module types
   (owner kinds, schema, interface mask, target phase) without factories; the binding to implementations lies in `CnCNew.Simulation`. The compiler follows the retail load order of the original, copies the `DefaultThingTemplate` with interface-mask rules
   into every object and types object headers and implemented module fields strictly through name tables from the reference sources.
   Canonical snapshots and every semantics not yet implemented (compatibility baseline `baselines/compatibility.json`)
   are reproducibly auditable. Details are in
   `docs/TYPED-DEFINITIONS.md` and `docs/PHASE3-COMPATIBILITY.md`.
5. `CnCNew.W3D` validates chunk trees and decodes mesh geometry, shader states, vertex materials, material/shader IDs, DCG/DIG/SCG vertex colours, prelit variants, texture tables and UV assignments independently of the renderer. A render plan groups triangles by their complete, ordered pass states. Mappers are compiled from attribute bits and strictly validated arguments into renderer-independent types and evaluated deterministically from explicit time. Repairs of known shipping defects take place exclusively in memory and are afterwards fully validated again.
6. `CnCNew.Images` decodes legacy image formats that Stride does not support directly. Since Phase 16 this includes `CursorReader` (Windows cursor files `.cur`/`.ani`: frames, hotspot, frame sequence and timing) for the software mouse pointer of the client. The TGA path processes the shipped uncompressed and RLE-compressed 24/32-bit files into normalised RGBA.
7. `CnCNew.Simulation` manages world, objects, behaviors, commands and the fixed tick. The project depends exclusively on
   `CnCNew.Data`: state consists only of integers and Q39.24 fixed point (since Phase 22; `FixedMath` derives arithmetic and trigonometry from the bit count, `SquaredReach` compares ranges without overflow, outside the simulation only `CnCNew.Presentation.FixedConvert` converts), the only random stream of the logic is the
   original generator (`logic`), there is no wall-clock time, no threads and no file, archive or content access (a
   source-code test enforces this). The world runs in fixed tick phases (commands, timers, updates, events, destroying, spawning, events,
   hash); mutations during an iteration go through queues. Modules are created through an explicit, sorted,
   reflection-free binding table (name → typed factory), which is checked against the data descriptors at start;
   presentation modules (`W3D*Draw`, `*ClientUpdate`) are never instantiated. The presentation later reads snapshots and events
   and writes only typed commands. Details in `docs/SIMULATION-CORE.md`. The game rules built on top of this (Phase 5:
   economy and supply, upgrades, combat with area damage, experience, teams/diplomacy, repair, simple movement, production, special powers, victory/defeat) remain the same layer – new modules and
   commands, no new dependency; details in `docs/GAME-RULES.md`. Phase 6 adds in the same layer terrain (`TerrainMap`,
   built from the `MapData` defined in `CnCNew.Data.World`, which `CnCNew.Formats` decodes from MAP files; the simulation reads
   no file), navigation (`NavigationGrid`), vision maps (`VisionMap`), build/sell commands and the skirmish AI (`SkirmishAi`), which as a
   pure issuer of commands reads only `EntitiesVisibleTo` and public start positions; details in `docs/SIMULATION-CORE.md` §13–§20.
8. `CnCNew.Client.Stride` projects exclusively simulation snapshots into the Stride engine chosen for the time being. `W3dStrideScene`, `W3dMaterialFactory`, `W3dTextureCache` and the depth-write pipeline processor separate mesh preparation, material translation, texture lifetime and pipeline states from program start. A W3D batch is executed as one Stride material with ordered passes; four UV and four colour streams receive the data that differs per pass. Animated mappers update dynamic vertex buffers from the deterministic W3D evaluation. The client maps alpha test, source/destination blend, depth compare/write and two-sided culling without a silent enum fallback. The client builds Stride's standard shaders with `Stride.Core.Assets.CompilerApp` into its local runtime database; Game Studio is not a build prerequisite.
9. **World-layer seam (Phase 7):** `RenderServices` and `IWorldLayer` separate the Stride scene into independent, exchangeable layers, which `LiveMatchHost` drives against a running `CnCNew.Game.LiveMatch`; `StrideConvert` translates simulation values (fixed point, cells, colours) losslessly into Stride types. Concrete layers: `Layers/Terrain` (heightfield, water, fog of war, minimap, `docs/CLIENT-TERRAIN.md`), `Layers/Objects` (W3D object/skeleton rendering and team colours on the existing material domain from item 8, `docs/CLIENT-OBJECTS.md`), `Layers/Fx` (particles, tracers, decals, `docs/CLIENT-FX.md`) and `Ui/UiRenderer` (2D draw-list renderer with FreeType text output through `Stride.SharpFont`, no `SpriteFont`/GDI, `docs/CLIENT-UI-RENDERING.md`). `Audio/AudioOutput` feeds `Stride.Audio` `DynamicSoundSource` instances from the renderer-independent `SoftwareMixer` of `CnCNew.Game.Audio`. Every layer reads exclusively snapshots/render projections and never writes into the simulation. `--match <map>` starts a controllable live skirmish, `--smoke-test --capture` generates a PNG headless for deterministic regression.
10. **`CnCNew.Game`** (new, Phase 7/8) is the Stride-free game logic between simulation and client: `GameData` loads compiled definitions/catalogues, `LiveMatch` drives a running match (tick advance, command intake, snapshot projection) without engine dependency, `Shell` reproduces the menu state machine (MainMenu/Options/SkirmishSetup/Loading/Score) from real WND layouts (`docs/GAME-SHELL.md`), `Hud` binds command bar, minimap and selection to real `ControlBar.wnd` data (`docs/GAME-HUD.md`), and `Audio` (`AudioDirector`, `EvaCatalog`, `MusicPlaylist`) selects music, EVA announcements and sounds deterministically from snapshot events (`docs/GAME-AUDIO.md`); the sound output itself stays in `CnCNew.Client.Stride/Audio`. `CnCNew.Game` references `CnCNew.Simulation`, `CnCNew.Data` and `CnCNew.Content`, but no Stride.
11. **`CnCNew.Presentation.Input`** (Phase 8) translates mouse, keyboard and hotkey events, modelled on `GameClient.cpp`, into typed simulation commands: `GameInputController`, `SelectionModel`, `CommandModeController`, `CommandBarModel` and `HotkeyMap` with a fixed translation order (meta keys, command-bar hotkeys, placement, GUI command, selection, camera, context commands); details and documented gaps in `docs/PRESENTATION-INPUT.md`. The layer reads only snapshots/selection state and writes exclusively typed commands into the simulation.
12. **Script execution and missions** (Phase 9) lie in `CnCNew.Simulation/Scripting` (`ScriptProgram`, `ScriptEngine`, `ScriptCoverage`) and `CnCNew.Simulation/Mission` (`MissionSession`, `MissionSnapshot`): a deterministic VM over the decoded `MapData.PlayerScripts`, which depends only on `CnCNew.Data`, issues commands as normal player commands and passes presentation actions to the client as `ScriptOutput`. Campaign flow and savegames (`CnCNew.Game/Campaign`, `/Save`) build on this and know neither Stride nor the shell; details in `docs/SCRIPT-ENGINE.md` and `docs/CAMPAIGN-AND-SAVEGAMES.md`.
Since Phase 11 skirmish and missions share the presentation layer through the abstract base `LiveGame` (`CnCNew.Game/Live`): `LiveMatch` and `LiveMission` each put a simulation behind it,
HUD (`MatchController`, `MissionController`), audio and Stride layers see only `LiveGame` (`docs/GAME-HUD.md` §14).
Since Phase 12 `CnCNew.Client.Stride/ClientRuntime` (with `Ui/StrideInputTranslator`) wires HUD draw list, input and shell outputs to the Stride client (`docs/GAME-HUD.md` §15); the client writes only typed inputs and reads only what the controllers show. The script objective driver (`CnCNew.Simulation/Testing/ObjectiveDriver*`) is test/tool code and not simulation behaviour (`docs/SCRIPT-ENGINE.md` §9). Since Phase 13 the aircraft, parachute, uplink and vehicle modules lie in `Modules/BuiltIn/FlightModules.cs` and `VehicleModules.cs` (`docs/SIMULATION-CORE.md` §28), the reinforcement with transport in `Scripting/ScriptEngine.Reinforcements.cs` and the AI team queues in `Scripting/ScriptEngine.TeamQueues.cs`; the simulation still depends only on `CnCNew.Data`.

Since Phase 14 the module catalogue of the simulation is complete (183 of 183 simulation modules, `docs/SIMULATION-CORE.md` §30): every object of the retail data can be instantiated. Which weapon an object fires is determined solely by the active `WeaponSet` selection of the weapon-slot model (`SimulationWorld.WeaponSlots`, state per slot only for objects with more than one weapon); presentation and scripts read the slots through `IWorldServices`/queries and write only typed commands (`FireWeaponCommand` with slot, `SetWeaponLockCommand`). Collision modules run through a single interface (`ICollideModule`, `SimulationWorld.DeliverCollisions`).
12. Stride takes over Direct3D, window, input and rendering (the sound output runs through `waveOut`, Stride's audio layer crashes on the development machine, `docs/GAME-AUDIO.md`); legacy compatibility stays in our libraries. Sound: `CnCNew.Game.Audio.GameAudio` (Stride-free: director, mixer, counters, offline renderer) is attached by the client through `ClientAudio` to exactly one consumer – the device (`AudioOutput`), a WAV file (`--audio-capture`) or nothing (`--smoke-test`); the simulation learns nothing of this. The editor is optional.

The W3D file fields `ColorMask`, `FogFunc`, `ShaderPreset` and padding are PS2 parameter storage in the shipped PC content. In accordance with the EA PC loader they are preserved losslessly, but not interpreted as a PC colour mask or fog state; PC colour writing is active and file fog is deactivated. Details, content values and image baselines are recorded in `docs/W3D-MATERIALS.md`.

The community patch is not copied wholesale over the original data. Every change stays assigned to an overlay layer and a documented fix. This way original behaviour, bug-fix mode and optional balance changes are comparable.

**Tick rate (since Phase 20):** the rate of the simulation is a value of the world (`SimulationRate`: 30, 60 or 120 Hz). The default of a session has been **60 Hz** since Phase 23 (`e8632bb`, 8 October 2026), defined in exactly one place (`ProductRate.TicksPerSecond` in `CnCNew.Game`, from it `GameData.DefaultSessionRate`); the simulation itself knows no default – whoever creates a world names the rate. Catalogues are built per rate, every time goes through the time service (`world.Time`), times from the data lie on the 30 Hz grid of the original; snapshot, replay and world fingerprint carry the rate. Outside the simulation (since Phase 21) there is exactly one rate constant, the original frame `CnCNew.Data.OriginalFrame.PerSecond` (1/30 s, the unit of the client content of the original); the presentation reads the game time from `GameClock` (tick, rate, interpolation fraction) and the rate of the session from `GameData.Rate`; `SaveGame` carries the rate (`docs/TICKRATE-MIGRATION.md` §14). **Above 30 Hz (since Phase 23)** the simulation subdivides the 30 Hz step instead of re-integrating with a smaller step size: an object decides in the first tick of its own original frame, reaches its 30 Hz position with the last one, and whoever looks at it reads its frame end (`Entity.FrameEnd`); the state for this is written only above 30 Hz, at 30 Hz every byte stays the same (`docs/SIMULATION-CORE.md` §43, exceptions "once per original frame" in §41.1). 30 and 120 Hz are checked by the rate-equivalence suite against 30 Hz as the definition (§39); golden hashes exist only at 60 Hz (`baselines/reference-manifest.json`), and a manifest is checked with the rate that its file names. Limits: not every match is identical between the rates (`docs/TICKRATE-MIGRATION.md` §15.7.6), and no human has seen the game at 60 Hz.

**Session core (since Phase 24, `docs/SIMULATION-CORE.md` §45, `docs/PRESENTATION-INPUT.md` §13):** a skirmish is started from a `MatchDescription` (`CnCNew.Simulation.Skirmish`), an immutable value with one binary encoding from which every machine builds the same tick 0; who plays locally is not part of it. The state of a session is the world plus every computer player plus the session counters, with one hash over all of it (`SkirmishMatchSession.StateHash`, `Save`, `Restore`). Orders leave the presentation as intents through `CommandPath` (`CnCNew.Presentation.Input`): pre-checked at once by `SimulationWorld.Check`, submitted as the bundle of their tick immediately before its step, answered by receipt number; `ICommandScheduler` decides the tick. `LiveGame.Advance` owns no time: an `ITickDriver` (`CnCNew.Game.Live`) releases the ticks, and pause and speed are requests to it. Both interfaces have local implementations only; the network ones are Phase 25. Nothing outside the simulation may name its logic random stream (source test).

**Network layers (since Phase 25, `docs/NETWORK-PROTOCOL.md`):** `CnCNew.Net` (messages and their codec, the command codec of the simulation on the wire, the build identity, the connection interface, the loopback network, the protocol client) references **only** `CnCNew.Simulation`; `CnCNew.Server` (room and relay as a library) references **only** `CnCNew.Net`, loads no game data, opens no file and decodes no command; `CnCNew.Game` references both and embeds the server for the local skirmish (`CnCNew.Game.Lockstep`: `LockstepDriver`, `LocalRelay`), so there is one match path. `CnCNew.Simulation` still references only `CnCNew.Data`. Wall-clock time exists in neither network layer: the only clock is the injected `INetClock`, and it paces - it never enters the simulation. No thread, no timer, no random source other than the loopback's own generator. The client never starts, steps or commands a session around the relay. All of it is enforced by the test "Layer rules" of `tests/CnCNew.Net.Tests`. **Since Phase 26** (`docs/NETWORK-PROTOCOL.md` §12 to §15, `docs/DEDICATED-SERVER.md`): `CnCNew.Net.Udp` is the UDP transport behind the same connection interface (BCL sockets only; a connection is a state machine without a socket, so its tests run on a datagram network in memory with a clock set by hand); the one file that reads real time is `CnCNew.Net/RealTime.cs` (the monotonic clock of a host and the request for a fine system timer) - the layer rule names it as its only exception; `CnCNew.Server.RoomDirectory` puts several rooms behind one endpoint; `tools/CnCNew.DedicatedServer` is the relay as a program and references `CnCNew.Net` and `CnCNew.Server` only (a test follows its references to the end: the simulation and its data model, never content, the game layer, the presentation or a renderer); `CnCNew.Game.Lockstep.HeadlessClient` is a client without a window, hosted by the tests, the multi-client probe and `tools/CnCNew.NetTool`. The window client still reaches a match only through its embedded server. **Since Phase 27** (`docs/NETWORK-PROTOCOL.md` §18, `docs/NETWORK-DIAGNOSTICS.md`): the window client has a second way to a match - `CnCNew.Game.Lockstep.RemoteRelay` (a UDP socket, the transport, the protocol client and `SystemNetClock`) and `LiveMatch.Join`, beside the embedded `LocalRelay`; both end in the same `LockstepDriver`, so the rule "one match path" holds. `CnCNew.Server` still opens no file: a finished room is handed to its host (`RoomDirectory.TryTakeFinished`) and the host - `tools/CnCNew.DedicatedServer` - writes the replay file through `CnCNew.Net.RecordingFile`. The relay still simulates nothing and reads no state: a session state that travels from one member to a joiner is bytes with a stated hash, which the relay compares with the hash all clients reported. What a client keeps for the diagnosis of a desync (`SessionDiagnostics`) and the packing of a state for the wire (`SessionTransfer`) live in `CnCNew.Game.Lockstep`; the simulation only gained two read-only views of its hash (`SimulationWorld.Diagnostics.cs`, `docs/SIMULATION-CORE.md` §48). Since Phase 28 the transport seals what it carries: `CnCNew.Net.Udp.UdpCrypto` (the handshake's key exchange signed by the server's permanent key, AES-256-GCM per datagram - base class library only, no package), and the limits of an open port live where the thing they bound lives - handshakes, connections and bytes in the transport (`UdpOptions`), messages, states, match length and recording in the room (`RelayOptions`, `RelayServer.Limits.cs`). The two network layers still open no file: the server's key, its ban list and its logs belong to the host program (`tools/CnCNew.DedicatedServer/Operation.cs`), the client's list of known servers and its player key to `CnCNew.Game.Lockstep` (`KnownServers`, `PlayerKeyFile`), and the transport asks its host whether a server's key is to be trusted. The simulation gained one rule: a player's command may not state a point beyond a coordinate limit, and `CommandTypes.IsPlayerOrder` says which commands may come over a wire (`docs/SIMULATION-CORE.md` §49).

**Planned, not yet built (scope change of 5 October 2026, `docs/MULTIPLAYER-PLAN.md` §2):** multiplayer skirmishes run as lockstep through a relay server. Two new layers are added: `CnCNew.Net` (messages, transport, lockstep driver of the client; references only `CnCNew.Simulation`) and `CnCNew.Server` (room and relay logic; references only `CnCNew.Net`, does not simulate and loads no game data), plus the program `tools/CnCNew.DedicatedServer`. `CnCNew.Game` embeds the same server for the local skirmish (loopback transport), so that there is only one match path. Wall-clock time exists only in these two layers and only for pacing; the simulation is driven solely by tick bundles. The skirmish AI becomes part of the hashed and saved session state and runs in the simulation of every client. The tick rate becomes a value of the world (supported 30, 60, 120 Hz; product rate 60 Hz), `Fixed` changes from Q47.16 to Q39.24. Until the respective phase is completed, the text above describes the actual state (fixed 30 Hz tick, Q47.16).

Since Phase 17 units choose their victims in the simulation themselves (`SimulationWorld.Acquisition`, `AttackMoveCommand`; `docs/SIMULATION-CORE.md` §33): issuers of commands (`SkirmishAi`, `MissionSession`, `StandingOrders` of the presentation) now name only explicit targets and march routes. The commands-only agent of the missions (`CnCNew.Simulation/Testing/ObjectiveDriver.Commands.cs`) remains test/tool code; the message list of the HUD (`CnCNew.Game/Hud/HudMessageFeed`) reads simulation events and writes nothing back.
