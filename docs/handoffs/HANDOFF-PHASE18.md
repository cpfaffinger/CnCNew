## Brief (in this order)

1. **Reproduce the starting state.** `git status`, clean build (0 warnings), all test programs, the audits, re-measure all reference values from `CLAUDE.md`. Clarify deviations from the docs first.
2. **Reference manifest (the new yardstick).**
   - `SimTool reference-manifest write <content> <datei>` and `… check <content> <datei>`: executes a fixed list of runs and writes or compares per run parameters, tick rate, end tick, winner, final hash and chain hash. Deterministic file (sorted, no paths, no timestamps).
   - Content at least: reference match, stress test, the 16 AI runs of the table in `docs/SIMULATION-CORE.md` §19, the three Alpine Assault pairings, three 8-player runs on different maps, `skirmish-sweep` as a summary, per campaign two maps `mission-run` with hash before and after save/load. Levels `--set quick` (minutes) and `--set full`.
   - In addition an **input manifest**: definition fingerprint, hash of the bone table, terrain fingerprint and file hash of all 150 maps, hash of the built catalogues. With it, in the case of a deviation between two machines, it can be separated whether already the inputs or only the computation deviates.
   - Stored under `baselines/` (contains only hashes and numbers, no original data). Every change of the file is subject to review like `baselines/compatibility.json`. The docs continue to name values, the manifest is authoritative.
3. **Determinism matrix.** The manifest (`check`, level `full`) runs under every row; the result is a table "row × identical yes/no × first deviation":
   - the same machine: Release and Debug; `DOTNET_TieredCompilation=0`; `DOTNET_TieredPGO=0`; `DOTNET_ReadyToRun=0`; `DOTNET_EnableHWIntrinsic=0`; `DOTNET_EnableAVX2=0`; server GC; a different operating system culture (e.g. `de-DE`, `tr-TR`, `ar-SA` via `CultureInfo.DefaultThreadCurrentCulture` in a test switch);
   - a different operating system on the same machine: the headless tools under Linux (WSL or container) against the same content (ICU instead of NLS, different C runtime);
   - a different .NET patch version, if installable;
   - **a second physical machine with a different CPU** (different manufacturer or different generation). That needs the human: write instructions (`docs/DETERMINISM.md`) on how tool and `.local/phase2-import-a` get there (copy locally, never commit). If the run does not take place, that is in the report as open – not as passed.
4. **Work through findings D1–D9.** First confirm or refute each with a test, then fix:
   - D1: compute the bone table so that the result does not depend on CPU, FMA or C runtime (e.g. chain in `decimal` or exact integer arithmetic, angle via an integer routine of our own); golden table hash in the input manifest.
   - D2: convert float bits to `Fixed` without a runtime routine. Preferably hash-neutral (own integer replica of the previous seven-digit rounding, checked against all float values of all 150 maps); otherwise as a named, measured hash change in a commit of its own.
   - D3: show whether any unordered enumeration influences the result (test: load the world from a snapshot after every checkpoint and let it continue in parallel, over the full manifest); where yes, order. If that changes hashes, it is a separate, measured change.
   - D4, D7: fix (ordinal comparers, invariant formatting, total order).
   - D5: identify maps via the file hash from the content manifest; complete the terrain fingerprint.
   - D6: extend `SourceRules` and introduce a second rule set for everything that feeds the simulation (`CnCNew.Data`, the map decoding in `CnCNew.Formats`, `ModelGeometryLoader`): there `float` is allowed as a file format, but every conversion into simulation inputs runs through exactly one checked routine.
   - D8: a check mode of the manifest that checks the incremental hash against the full one in every tick (short runs) uncovers missing `MarkDirty`.
   - D9: fingerprint via an own, fixed encoding instead of via the escaping of the runtime, or a golden value across the matrix.
5. **Performance profile (quiet machine, nothing in parallel).**
   - `SimTool perf <content> --map … --players N --ticks T`: the time per tick, from it mean, 50/95/99 % quantile and maximum; breakdown by tick phase (commands, timers, updates, collision, vision, events, hash) and AI; allocations and GC runs; object count over time.
   - Runs: 2, 4 and 8 players on at least three maps of different size, 54,000 ticks each (30 game minutes at 30 Hz); in addition playback without AI (catch-up speed as a multiple of real time), writing/reading a snapshot together with its size at the end, two large missions.
   - Leads from the search run, **not verified**: the vision hash is recomputed every three ticks over every cell for every player (`VisionMap.cs:132–149`); `Describe` hashes template, module and tag names character by character; `MissionSession.StateHash()` describes the script state completely every time.
   - Result: a table and a projection to 60 Hz. It is the input for Phase 19; nothing is optimised here.
