## Brief (in this order)

1. **Wire the sound (item 7).** Create and operate `AudioDirector` (`CnCNew.Game/Audio`) and `AudioOutput` (`CnCNew.Client.Stride/Audio`) in the client: mixer lifetime, device start/end, pumping per frame/tick, events from the simulation (shots, explosions, building, unit voices on selection/command, EVA announcements such as "Base under attack"), UI sounds (clicks, menu), music (playlist per game phase/faction/campaign), volume sliders and mute from the options, clean behaviour without an audio device (warning, no crash; `--smoke-test` stays device-free). Make it measurable: counters per source (started/ended/discarded voices, missing sound files) in the console report, a capture mode that writes the mixer output as WAV (for a reproducible checksum comparison and for listening), tests for the wiring. The docs (`GAME-AUDIO.md`, README, `DEMO-FINDINGS.md`) are corrected first, and only then is "done" reported.
2. **Mouse cursor (item 8, part 1).** Display cursors from `Mouse.ini`/`MouseCursor` (ANI/TGA cursors of the original data, animation frames, hotspot) in the client and change them per context: move, attack, select, gather, repair, enter, sell, not allowed; modifier keys (Alt, Ctrl, Shift) act on the cursor immediately (e.g. Alt = waypoint/attack-move mode according to `CommandMap.ini`), command modes from the command bar set the cursor, edge scroll cursor. The operating system mouse is hidden or replaced by a software cursor; tests: context → cursor name (table from `docs/PRESENTATION-INPUT.md` § context commands against `Mouse.ini`), smoke test without missing cursor images.
3. **Make waypoints and standing orders visible (item 8, part 2).** Draw set waypoints (commands with Alt: `StandingOrders`), rally points of production buildings, movement targets and attack targets of the selection as lines/markers above the terrain (original behaviour: waypoint line with flags, rally point flag at the building, target marker when a command is issued), only for the own selection or while holding Ctrl/Alt; data flow via snapshot/`StandingOrders`, no simulation dependency of the presentation. Test: command sequence → expected marker list; `--capture` scene with three waypoints for the visual check.
4. **Texts (item 10).** Comparison with the original: font (`Fonts` from INI/WND, size/weight), tracking and line spacing (FreeType vs. GDI), umlauts and special characters, line wrapping and truncation in WND elements, alignment, colours/shadow/outline, CSF strings (placeholders `%s`/`%d`, language selection, fallback for a missing entry – counted, never silent). Result: capture set (main menu, options, command bar, tooltips, briefing, loading screen, mission text) plus a findings table "element × deviation × cause", fixed causes with a test; remaining deviations named.
5. **Mission in the client (item 9).** Show what really happens in `--mission`: does `MissionSession.Step()` (and with it the script VM) run every logic tick, same side/persona as in the test, intro/timers, loading process? Are the **outputs of the VM** (`ScriptOutput`: camera actions/camera rail, text/subtitles/speech bubbles, speech and sound, film sequences, radar events, countdown/counter displays, input lock, letterbox/fade, mission objectives/victory overlay) consumed and displayed (counters per type in the console report, "passed through" vs. "displayed")? One human scenario per map (e.g. `GC_ChemGeneral`, `MD_USA01`, `MD_GLA03`): the intro runs, the objective appears, the victory/defeat screen comes. What is missing (film without a Bink decoder, sound, camera rails) is counted, named and – where possible – solved by an honest substitute display (still image/text), not skipped.
6. **Clicking through shell → campaign → mission → save/load → completion** (`demo-shell.ps1`) and skirmish setup → match → result with a human; list of findings with cause; fix fixable errors (loading errors, dead buttons, wrong selection, crashes). The report lists per screen "worked / did not work / worked with defects".
