## Honest status (starting point, verified against the code of 5 October 2026; re-check line numbers)

1. **The AI lies outside the world state.** `SkirmishMatchSession.Step()` calls `ai?.Update()` per tick and then `World.Step()` (`src/CnCNew.Simulation/Skirmish/SkirmishMatchSession.cs`). `SkirmishAi` holds around 30 fields of its own state (memory of seen opponents and depots with timestamp, order and retry tables, running production, rally and scouting targets, avoided places, its own `SageRandom` stream; field list in `SkirmishAi.cs`). None of it is in the `WorldSnapshot` or in the state hash. Consequences: (a) `SkirmishMatchSession.CreateSave()` deliberately throws `NotSupportedException`; (b) in lockstep a deviation in the AI state would go unnoticed until the worlds diverge; (c) a rejoin via snapshot is impossible.
2. **The AI uses unordered collections** (`Dictionary`, `HashSet` next to `SortedDictionary`/`SortedSet`). Whether a decision depends on their enumeration order is not verified (consult the finding of the determinism audit from Phase 18).
3. **The command path answers synchronously.** `ICommandSink.Issue(Func<ulong, long, SimCommand>)` (`src/CnCNew.Presentation/Input/CommandSink.cs`) returns a `SubmitResult` immediately; the caller gets the sequence number and **the current tick** (`World.Tick`) and builds the command with them. `CommandModeController` displays a rejection immediately. On the network both are wrong: the server assigns the execution tick, and whether a command is accepted is only certain at execution.
4. **The world can accept commands for later ticks** (`SimulationWorld.Submit`: list per `command.Tick`) – that is the basis for lockstep and already present. But two properties make the *time of submission* a showstopper: (a) `Validate` already checks at submission against the **current** world (player, sequence, existence and ownership of the target, templates, upgrades …) – two clients that submit the same command at different times can accept or reject it differently; (b) every accepted command enters the state hash immediately (`_commandSum`). In addition there is (c) the order: the replay submits sorted by (player, sequence) (`ReplayRunner`), the live session in output order (human, system, AI). From this follows the rule for everything else: **every command for tick T is submitted on every machine at the same tick boundary and in the same canonical order.**
5. **`LiveGame.Advance` owns the time.** Accumulator from wall-clock time, at most 8 ticks per frame, `Speed` and `Paused` as local properties (`src/CnCNew.Game/Live/LiveGame.cs`). On the network the server determines which ticks exist.
6. **The match input is incomplete and not transferable.** `MatchSetup` knows map path, faction of the human, opponent list, seed and options; teams exist only in `SkirmishSlot`, colours, start positions and AI strength not at all (the skirmish setup shows the selection fields but does not pass them on). The human is fixed as player 1.
7. **The AI commands are in the replay** (`SkirmishMatchSession.Submit` records every command); playback therefore does not need the AI.
8. **The AI seed is nowhere.** `AiSeed` (per AI `AiSeed + index * 7919`) is neither in the replay header nor in the snapshot; the random choice of a faction in the skirmish setup draws from the shell's own `System.Random` (`SkirmishScreens.cs`). Both must follow from the match description.
9. **`SimulationWorld.LogicRandom` is public.** No code outside the simulation reads it today; in lockstep a single access from presentation or a tool would be a desync. Restrict the access or forbid it by a source test.

5. **Replay.** Header = match description; content = commands of the humans and of the system. During playback the AI runs along. The AI commands remain in the replay as an **audit trail**: playback compares the newly generated AI commands with the recorded ones and reports the first deviation with tick and player – a cheap, very sharp determinism tool. Increase the replay format.
6. **Two-stage command path.**
   - The presentation hands over a **command intent** without tick and without sequence. It immediately receives (a) the result of a **local pre-check** against the current state (the same checks that the simulation makes at execution, as far as they are possible without a state change) and (b) a receipt number.
   - The execution tick and the sequence are assigned by an `ICommandScheduler`: locally "this tick", on the network the server.
   - The final result comes as an event at execution, assigned via the receipt number. Display, sound and statistics (`CommandIssued`, `CommandFeedback`, `NoCanDo`) hang on pre-check *and* result; if the result deviates from the pre-check, that is counted.
   - `StandingOrders` and all other places that generate commands per tick (`BeforeTick`) go the same way and must stay correct with delay (no duplicate, no late command).
7. **Tick source.** `LiveGame.Advance` asks an `ITickDriver` which ticks may run now and with which commands: locally the previous accumulator; for the probe below and for Phase 25 a driver that releases only ticks whose command bundle is present. Commands of a bundle are submitted **immediately before the step of their tick** (finding 4). Pause and speed become requests to the driver.
8. **Lockstep probe in the same process.** A driver with an artificial input delay of d ticks: at d = 0 all reference values are identical to step 1 (that is the proof that the rebuild changed nothing); at d = 4 and d = 12 (around 67 and 200 ms at 60 Hz) match and mission run without errors, the user-interface tests for delayed acceptance and rejection pass, and the human can try it out in the client (`--input-delay-ticks N`).
9. **Mission.** `MissionSession`/`LiveMission` use the same interfaces with the local implementations. The feedback of the presentation to the script VM (camera done, speech done, `PresentationLatencyTicks`) is wall-clock-dependent input into the simulation and therefore remains explicitly restricted to local missions; record in the docs that exactly this would stand in the way of a networked campaign.

## Bottlenecks and showstoppers of this phase

- **AI cost with eight players.** Seven AIs compute on every client. Today `Observe()` runs every 5 ticks per AI, `Think()` every 15 (expressed in game time since Phase 20). Measure the cost per AI; offset the thinking times of the AIs against each other (deterministically, from the player number) so that they never all compute in the same tick.
- **Pre-check without side effect.** The local pre-check must change no state and draw from no random stream of the logic; a test compares the hash before and after 10,000 pre-checks.
- **Sequence numbers.** Today every source counts by itself (human, AI, system). With assignment by the server the rule "strictly increasing per player in submission order" must still hold, even if AI commands come locally and human commands via the bundle (separate number ranges per source or assignment at submission – decide, document, test).
