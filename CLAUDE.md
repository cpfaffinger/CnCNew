# CnCNew – working instructions for coding agents

Local C#/.NET 10 reimplementation of the SAGE runtime needed for *Command & Conquer: Generals – Zero Hour*
(Windows client with Stride 4.3 / Direct3D 11). Scope of the first product:
single player (skirmish and campaign) and – since the scope change of 5 October 2026, planned and
not yet built – multiplayer skirmishes through dedicated servers (`docs/MULTIPLAYER-PLAN.md`). Since
Phase 23 (8 October 2026) the simulation runs at 60 Hz by default (the rate is a value of the world, 30 and 120 Hz remain supported); the
multiplayer part is still only planned. Not in scope: networked campaign, matchmaking/ladder, NAT traversal,
GameSpy compatibility, anti-cheat, binary compatibility with old mods and savegames.
The repo has been public since 9 October 2026: remote `origin` = `https://github.com/cpfaffinger/CnCNew.git`, branch `master`
(no CI, no branch protection). Licence `GPL-3.0-or-later` (`LICENSE.md`, `NOTICE.md`). It contains **no game data** and must never contain
any (sections "Local data" and "Git rules"). The target platform is **Windows only** for the time being; acceptance runs under Windows, Linux
comes into consideration later only as host of the dedicated server (decision of 9 October 2026, `docs/MULTIPLAYER-PLAN.md` §7).
The documentation is indexed in `docs/README.md`; phase briefs lie in `docs/handoffs/`, the package reports of Phase 23 in
`docs/rate-invariance/`.

The overall planning is in `docs/plan/PROGRAMME.md` (since 10 October 2026: four stages – 1 port, 2 engine, 3 changes,

## Layers and hard dependency rules

Import → runtime content → data models → simulation → presentation. Layers stay separate.

- BIG archives and import VFS exist only in `CnCNew.Archives`, `CnCNew.IO`, `CnCNew.Import`.
- Runtime code opens only materialised files through `CnCNew.Content` (schema 2).
  `CnCNew.Content` references neither `CnCNew.Archives` nor the import VFS.
- `CnCNew.Import` is the only connection between import VFS, formats and runtime contract.
- `CnCNew.Data` is independent of renderer, engine, archive and file system. `IniNode` never leaves the
  compiler; simulation and presentation see only `CompiledDefinitionGraph`.
- `CnCNew.Simulation` depends only on `CnCNew.Data` (the test `SourceRules` enforces this and forbids wall-clock time, ambient random numbers, `float`/`double`, threads, file/process access and reflection in the source code): no Stride, no DirectX, no
  UI, no content/archive/file-system access, no wall-clock time, no threads in the core,
  no `Random.Shared`, no dependence on reflection order.
- Stride types stay in `CnCNew.Client.Stride`.
- Network layers (since Phase 25, `docs/NETWORK-PROTOCOL.md`): `CnCNew.Net` references only `CnCNew.Simulation`; `CnCNew.Server` references only `CnCNew.Net`, loads no game
  data, opens no file and decodes no command; `CnCNew.Game` embeds the server for the local skirmish. Neither network layer reads wall-clock time, starts a thread or a
  timer, or draws from a random source other than the loopback's own generator - the only clock is the injected `INetClock`. The client starts, steps and commands no
  session around the relay; in `CnCNew.Game` only `LiveMatch` and `CnCNew.Game.Lockstep` build a skirmish session (headless tools and tests may step one directly: they are
  the reference). The test "Layer rules" of `tests/CnCNew.Net.Tests` enforces all of it. Since Phase 26: the one file of the two network layers that reads real time is
  `src/CnCNew.Net/RealTime.cs` (`SystemNetClock`, `FineTimer`) - the rule's only exception, do not add a second; `tools/CnCNew.DedicatedServer` references `CnCNew.Net`
  and `CnCNew.Server` only (a test follows the references to the end and reads its source); what a running match must not wait for behind a lost packet goes on the
  urgent channel (`IConnection.SendUrgent`), and order holds per channel, not between the two. Since Phase 27: `CnCNew.Server` still opens no file - a finished room is
  handed to its host (`RoomDirectory.TryTakeFinished`), and the host writes the replay; the relay passes a session state on unread, by its stated hash; the window
  client reaches a foreign server only through `CnCNew.Game.Lockstep.RemoteRelay` and `LiveMatch.Join`, which end in the same `LockstepDriver` as the embedded relay.
  Since Phase 28: cryptography is the base class library's and lives in `CnCNew.Net.Udp.UdpCrypto` only - no cipher of our own, no package; a key, a list of bans or
  of known servers and a log are files of the host program (`tools/CnCNew.DedicatedServer/Operation.cs`, `CnCNew.Game.Lockstep.KnownServers`/`PlayerKeyFile`), the
  two network layers still open none and are handed what they need (an identity, a `trust` callback, `isBanned`, `IsKeyBanned`); every limit of the transport and
  the room is an option with a counter and a defined reaction (`UdpOptions`, `RelayOptions`; `docs/DEDICATED-SERVER.md` §9.2) - a new message or a new thing a member
  can make the server keep needs its bound, its counter and its line in the threat model; whatever arrives from a wire is counted and dropped, never thrown
  (the suite "Fuzz" of `Net.Tests` feeds every parser; a finding goes into its corpus).
- The presentation reads immutable simulation snapshots and writes only typed input commands.

## Non-negotiable quality rules

- Unknown keys, modules, enums, units or references **never** fall back silently to
  default values. Every compatibility case is explicit, counted, documented and secured against drift by
  `baselines/compatibility.json` (`IniTool compat-check`, real-data test of the data tests);
  changes to this file are subject to review.
- The simulation reads only what `CnCNew.Data` delivers strictly typed; unimplemented modules make an object
  non-instantiable and are listed in `MissingModules`, they are never silently ignored. New simulation modules
  need catalogue schema, binding, tests and an entry in `SIMULATION-CORE.md`.
- Determinism: canonical sorting, no absolute paths, timestamps or
  Dictionary/HashSet orders in artefacts. Two independent runs must be byte-identical.
- `TreatWarningsAsErrors=true`. The clean build has **0 warnings** (`dotnet build CnCNew.slnx` with deleted `bin`/`obj` of
  `CnCNew.Client.Stride` and `dotnet build tools/CnCNew.UiRenderTool`; measured 5 October 2026). Every warning is an error until it
  is fixed. The former 11 `EXEC` lines of Stride's `Stride.Core.Assets.CompilerApp` (`[YamlAssemblyRegistry] Assembly [CnCNew.…]
  has not been processed by assembly processor …` per referenced project, `[AssetCompiler] Could not find game settings asset …`)
  do not apply to this repo (no Stride assets in the CnCNew assemblies, no Stride GameSettings asset) and are classified by
  `build/StrideAssetCompile.targets` (through `Directory.Build.targets`) specifically as ordinary tool output: exactly these two
  patterns, every other warning/error line of the asset compiler stays a warning/error. Cross-check:
  `dotnet build src/CnCNew.Client.Stride "-p:CnCNewStrideKnownAssetCompilerNotes="` shows them again. The file copies the target
  `StrideCompileAsset` from Stride 4.3.0.2507 and is to be checked against the package on a Stride update; do not extend the exception list
  without verifying the cause. `NU1901`/`NU1903` were real advisories of the transitive Stride tooling packages and have been fixed since Phase 15 by
  `build/StrideToolingPins.props` (do not suppress them again); `scripts/audit-vulnerable.ps1` checks the solution and
  `CnCNew.UiRenderTool` for known vulnerabilities and belongs to the completion of a phase. Older numbers (21 or 11 warnings) further below and in
  the phase reports are historical.
- No trust in numbers from docs or earlier reports: always re-measure content numbers.
- Foreign code (EA sources, GeneralsGameCode, GeneralsGamePatch under `references/`) may be read,
  but not copied unexamined. Algorithms are understood, rewritten and justified in the
  doc with a source reference (file, function).
- New NuGet dependencies only with a justification; BCL preferred.

## Local data (never commit)

- `game/` – the developer installation in the repository: the same layout as a user installation (`game/content` =
  schema 2 runtime content of open files, `game/install.json`, optionally `game/bin`), generated from the English Steam installation
  (the only supported source version, described in `baselines/steam-master.json`) by `scripts/dev-content.ps1`.
  Users install with `scripts/install.ps1` to `%LOCALAPPDATA%\CnCNew\Game` (`docs/INSTALLATION.md`).
- `.local/` – other local working data (captures, measurement logs, definition snapshots). The former asset directories
  there (`game-original`, `assets/by-archive`, `content` = schema 1, `phase2-import-a`/`-b`, `manifests`, snapshots) no longer exist.
- `references/` (EA source code, GeneralsGameCode, GeneralsGamePatch, Stride – read only), `bin/`, `obj/`, `.idea/`, `.vs/`, `artifacts/`,
  `.claude/` (agent worktrees and local settings).

Original assets, generated artefacts and own source code stay legally and technically separate.
Test fixtures are small, synthetic and legally unobjectionable (no excerpts from original files).
Temporary outputs belong in the scratchpad of the session, not in the repo.

## Build, tests, audits

**Test strategy (binding since 10 October 2026, `docs/TESTING.md`): checks are chosen by what a change can break, in four tiers –
the whole run is not run for every change.**

- **Tier 1 focus** while working: the one test or suite of the changed code (`Simulation.Tests -- --only "<part of the name>"`,
  `Game.Tests -- --only <Suite>[,<Suite>]`, `reference-manifest check … --only <id>`).
- **Tier 2 affected** before **every commit**: `pwsh scripts/test.ps1` – build with 0 warnings and the test programs of the touched
  areas, selected from the changed paths (minutes).
- **Tier 3 gate** before a **push** that contains more than documentation or scripts, and before merging a parallel worktree:
  `pwsh scripts/test.ps1 -Tier gate` – adds the consumers, the other tick rates and, for everything that feeds the simulation, the
  input manifest and the quick reference set.
- **Tier 4 full** only at its triggers: `pwsh scripts/test.ps1 -Tier full` – completion of a phase; a commit that writes a manifest
  under `baselines/`; a cross-cutting change of the simulation (`Numerics`, `Random`, `Time`, state hash, snapshot, replay, command
  versions, enumeration order, any format version); a change of the build (SDK, packages, `Directory.Build.*`); a deviation of the
  quick set that was not intended; before a tag or package; at the latest after ten pushed commits that touched simulation, data or formats.
- Rules: a failure is fixed at the tier that found it and that tier is run again; a manifest deviation is a finding, never a number to
  adopt; an unknown path counts as "everything"; a defect that escaped its tier 2 gets a focused test with its fix; every report
  names the tier that ran and what was not run – "all tests green" is said only after tier 4; a step skipped for lack of
  `game/content` is not a pass. `pwsh scripts/test.ps1 -Plan [-Tier …]` prints the steps and their commands.
- `pwsh scripts/audit-publish.ps1` before every push is independent of the tiers and unchanged.

## Git rules

- Remote `origin` = `https://github.com/cpfaffinger/CnCNew.git`, branch `master`. **Work on `master` only, no branches:** no
  feature branches are created or pushed; temporary local worktree branches of parallel agents are merged into `master`,
  deleted and never pushed. **When a task is finished, commit and push to `origin master` without asking** (standing
  instruction of the project owner, 9 October 2026). Never force-push, do not create a further remote.
- **Never commit or push game data or anything exported from it:** nothing from `game/` and `.local/`, no captures
  (images, sound, film strips), no world/mission snapshots and savegames from real data, no content manifests, no
  definition snapshots (`IniTool compile`), no extracted texts, graphics, models, maps or sounds. Allowed are
  checksums, sizes, names and counts of game files (this is how they stand in `baselines/`) – file contents are not. Test fixtures
  stay synthetic.
- **Before every push run `pwsh scripts/audit-publish.ps1`** – no game assets or anything exported from them ever reaches the
  repository. It runs the two history checks (both must end without a hit; a hit is clarified before the push, not after it):
  `scripts/audit-history-assets.py` compares every blob of the entire Git history by SHA-256 with every file of the installation
  and of the exported runtime content; `scripts/audit-history-excerpts.py` searches for verbatim lines from the text files of the game
  in all blobs (known and permissible: individual `key = value` lines in synthetic test fixtures). State of the first
  check on 9 October 2026: 4,605 blobs, 0 binary, 0 equal to a game file.
- Several commits per phase, each self-contained in subject matter (implementation, tests, docs separate where
  sensible). Before every commit check `git status` and stage selectively (`git add <files>`).
- Before every commit of code `pwsh scripts/test.ps1` (tier 2), before every push of code `pwsh scripts/test.ps1 -Tier gate`
  (tier 3); a documentation-only or script-only change needs neither (`docs/TESTING.md`).
- No destructive commands (`reset --hard`, `clean`, `checkout .`, force operations). Preserve foreign or
  unexpected changes. Published history is not rewritten.
- No `--no-verify`. Working tree clean at the end of a phase.
- Line endings: `.gitattributes` sets `* -text` – Git converts nothing, every file keeps its own line endings
  (`git ls-files --eol <file>` before editing, `git ls-files --eol -m` afterwards).
- Platform: acceptance runs (build, tests, manifests, audits) count under Windows. A Linux run (WSL) is informative and not an
  acceptance criterion (`docs/DETERMINISM.md` §5).

3. Implement, each time with tests: tier 1 while working, tier 2 before every commit, tier 3 before every push of code
   (`docs/TESTING.md`); the full run only at its triggers and at the completion (step 5).

5. Tier 4 and the completion checklist of `docs/TESTING.md` §8; commits, clean working tree, final report with numbers, commit
